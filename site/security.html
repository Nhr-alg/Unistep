Security

Last updated: October 27, 2026

UniStep is local-first. The solver, the worksheet generator and the practice bank run entirely in your browser. This page states exactly what stays on your device, what a synced account adds, and how that account is protected.

What stays on your device

  • Your problems and derivations. Solving never calls a server. The engine is JavaScript delivered with the page.
  • Photos. Image text recognition (OCR) runs locally in a WebAssembly worker. The image is not uploaded.
  • Generated worksheets and keys. Built in the browser; printing and CSV export use local browser APIs.

What a synced account adds

If you create an account on a deployment that has a server, the following is stored so your archive follows you between devices:

  • The problem text you solved, a short answer preview, the tag you applied, and the timestamp.
  • Your username and a salted scrypt password hash. The plaintext password is never stored, in the browser or on the server.
  • Nothing else. Full derivations are recomputed on your device when you reopen an entry, so the working you see is always produced by the current engine.

If no server is reachable — static hosting, offline, or the file opened from disk — accounts fall back to local profiles and the app behaves exactly as before.

How the account layer is built

  • Password hashing: scrypt (N=16384, r=8, p=1) with a 16-byte random salt per user, compared in constant time.
  • Sessions: 32 random bytes as an opaque token in an HttpOnly, SameSite=Strict cookie. No token is ever written to JavaScript-readable storage.
  • Login timing: unknown usernames still run the full key derivation, so response time does not reveal which accounts exist.
  • Cross-site requests: state-changing endpoints reject any request whose Origin does not match the host.
  • Rate limits: sign-up, login, archive writes and the waitlist form are all rate-limited per address.
  • Input handling: archive payloads are rebuilt field by field with length caps; nothing from a client is written through verbatim.

How the pages are built

  • A strict Content-Security-Policy on every page: no inline scripts, no inline styles, no third-party scripts, no framing.
  • No eval(). The grapher uses a hand-written recursive-descent parser, so a pasted expression is data, never code.
  • User text reaches the page through textContent and DOM construction, not HTML strings.
  • Static file serving resolves and checks every path, blocks traversal, and refuses to serve the data directory or server source.

What we do not do

  • No advertising or third-party analytics scripts.
  • No selling or sharing of personal data.
  • No claim of end-to-end encryption. Archive data is stored readable on the server so it can be synced; treat it as you would a shared document.
  • No claim of a completed third-party security audit. None has been performed.

Known limits

  • The reference server is a single Node process with JSON-file storage. It is sized for a pilot, not a multi-region deployment.
  • Anyone with access to an unlocked browser profile can read the local archive. Local profiles are a convenience selector, not an authentication boundary.
  • The 10-solve free limit is stored in browser storage and can be reset with developer tools. It is a product limit, not an access control. Paid access will need server-side entitlements before billing opens.
  • There is no password reset flow yet. A forgotten password means a new account.

Reporting a problem

If you find a vulnerability, please report it before disclosing it publicly. Use the contact link in the site footer; a dedicated security address is published once the domain and mailbox are live. We will confirm receipt and tell you what we intend to do.
